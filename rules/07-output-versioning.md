# 07 — Output and Versioning Rules

## Filenames

Use clear, descriptive filenames.

Preferred pattern:

`<Document Name> - <Status or Revision>.ext`

Examples:
- `Shareholder Loan Memorandum - Reformatted.docx`
- `Revenue Model - Revised.xlsx`
- `Accounting Manual - Client Ready.docx`

Avoid:
- `final_final_v2_REAL.docx`
- unclear abbreviations,
- random timestamps unless requested.

---

## Version behavior

Do not overwrite a user's source file unless explicitly instructed.

Default:
- preserve original,
- create a revised output.

For multiple iterations:
- keep the same logical base filename,
- add a simple revision indicator only when needed.

---

## Delivery

When delivering a completed artifact:
1. provide the downloadable file,
2. state the main changes in a short list,
3. disclose material unresolved limitations,
4. do not claim successful QA unless QA was actually performed.

---

## “Fixed” standard

Do not say:
- “fixed,”
- “corrected,”
- “resolved,”
- “all good,”

unless the relevant final artifact was checked after the edit.

If only code was changed but the output was not rendered/opened/verified, say:
- “updated,”
- “revised,”
- or “generated,”
and identify the remaining verification step.

---

## Content-change disclosure

If a task was intended to be formatting-only, verify that:
- paragraph text remains the same,
- table text remains the same,
- values remain the same,
- formulas remain the same.

If substantive changes were made, summarize them separately from formatting changes.
